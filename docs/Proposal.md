## The design problem

A student preparing a small-run poster can easily design with eight or more screen colours, then discover that the available press supports only a few inks. Choosing which colours to merge is both a production decision and a design judgment. A simple nearest-colour replacement ignores the combined setup cost of the chosen inks; manual trial and error becomes difficult as the palette and stock catalogue grow.

## Proposed application

OVERPRINT is a local web studio that maps a target artwork palette to available stock inks. It selects an approximate low-cost ink cover, shows the resulting colour shifts on an original SVG study, and identifies the colours a designer should inspect first. It exposes the intermediate algorithm decisions instead of hiding them behind a single score.

## Target users and workflow

Student designers, small creative studios and print-workshop coordinators. The user enters or imports a palette, enables available inks, adjusts relative setup costs and a colour tolerance, runs the Java planner, reviews the colour mapping, then exports the plan and specimen proof. A press limit is checked after planning and reported independently from colour coverage.

## Scope of the prototype

The prototype edits the palette of a fixed, original SVG specimen. It does not extract colours from arbitrary images. D65 CIELAB distance supplies an understandable screen-colour proxy; physical ink mixing, paper and printer calibration are outside scope. The product supports design decisions rather than claiming a press-accurate preview.

# Methods & evidence

A design decision with visible working.

TECHNIQUE | ROLE AND SYLLABUS FIT
--- | ---
Weighted greedy set cover | Unit 5: an ink covers target colours within a Delta E threshold. Select minimum cost per newly covered colour. Approximate weighted setup cost; do not claim exact optimality.
Randomized Quickselect | Unit 6 / CO5: find the top-k error boundary and nearest-rank p90 without sorting the full error list. Random pivots; reproducible seed; expected linear time.

## Architecture and data

A plain HTML/CSS/JavaScript frontend communicates with a Java HTTP API. The Java application validates input, converts colours, constructs the coverage matrix, runs both assessed algorithms and returns assignments, warnings and a decision trace. All core logic is self-implemented. No database or external account is needed.

Synthetic data includes a poster palette, packaging palette, infeasible neon palette, exact-match case, duplicate case and invalid-empty case. Stock costs are relative weights, not market prices. Larger algorithm-only datasets are seeded and generated by the benchmark runner.
